# Пакетная загрузка людей

Мастер: `/people/import`. Ссылки из общих страниц `/people` и `/data` добавляет их владелец. В мастер не передаются исходные документы на диске: архивы обрабатываются в памяти и не записываются в `data` или `uploads`.

## Интеграция

- Нужны ExcelJS, fast-xml-parser, unzipper; `Person.birthDate String?`, `ImportReceipt { id String @id, result String, createdAt DateTime @default(now()) }`; общий `PERSON_FIELDS` и `PersonFieldKey`.
- Все API вызывают `await requireUser()`; пойманный `Response` возвращается без подмены. Изменяющие запросы проходят общую проверку origin.
- При общем logout/блокировке хранилища вызовите `clearBatchImportJobs()` из `lib/batch-import/jobs.ts`. Общие auth/vault-файлы находятся за областью этого изменения. До подключения хука неиспользуемые задания удаляются по TTL (фоновая проверка раз в минуту); повторный вход получает другую привязку к cookie.
- Записи выполняются через `prisma` из `lib/db.ts` внутри callback `$transaction`. Журналирование и шифрование остаются ответственностью общего слоя. События, участия, вложения и восстановление архивных карточек без явного выбора не создаются.
- Успех сбрасывает RTK Query tags `People`, `Person`, `Search` и обновляет маршрутизатор; FTS обслуживается SQL-триггерами.

## API

| Запрос | Содержимое |
| --- | --- |
| `POST /api/batch-import/jobs` | Multipart `files` (несколько); возвращает `JobView` с таблицами и предложениями колонок. |
| `GET /api/batch-import/jobs/:id` | Текущий `JobView`; только владелец сессии. |
| `DELETE /api/batch-import/jobs/:id` | Отмена и удаление из памяти. |
| `POST /api/batch-import/jobs/:id/plan` | `{ revision, tables?, rowEdits?, decisions? }`; массивы заменяют соответствующий набор. Изменение таблиц сбрасывает исправления и решения; изменение строк сбрасывает решения. Возвращает новую версию задания и плана. |
| `GET /api/batch-import/jobs/:id/candidates?q=...` | До 50 ручных кандидатов, включая архив; запрос от двух символов. |
| `POST /api/batch-import/jobs/:id/candidates` | `{ revision, personId }`; проверяет существование карточки и регистрирует её как разрешённого ручного кандидата. |
| `POST /api/batch-import/jobs/:id/apply` | `{ version, confirm: true }`; применяет план или возвращает сохранённый результат. |
| `GET /api/batch-import/jobs/:id/receipt?version=...` | Только чтение сохранённого результата; отсутствие receipt возвращает 404 и не применяет задание. |

`rowEdits`: `{ rowId, excluded?, values?, acknowledgeWarnings?, separate?, mergeWith? }`. Пустое исправление исключает значение этой строки из импорта, не очищая поле в базе. `mergeWith` — ID исходной строки другого человека пакета; противоречия остаются видимыми.

`decisions`: `{ groupId, action: 'auto'|'new'|'existing'|'skip', personId?, restore?, fields? }`. `fields` содержит только ключи реестра и окончательные строки либо `null` («оставить текущее / не добавлять»). Подмена произвольных колонок Prisma не допускается. Новые ФИО обязательны; неоднозначности, ошибки и непроверенные предупреждения блокируют выбранную группу. Её можно пропустить и сохранить остальной пакет.

Идентификатор receipt вычисляется из задания и владельца сессии. Receipt и карточки сохраняются одной транзакцией. Повтор работает после удаления задания из памяти и перезапуска процесса с той же сессией. Receipt содержит только количества и ID карточек. Другой cookie или другая версия не могут повторно использовать этот receipt.

Мастер сохраняет ссылку на черновик отдельно от отметки об отправленном подтверждении. Последняя появляется только после вызова fetch для явно подтверждённого плана. При восстановлении после ошибки/перезагрузки кнопка результата вызывает только GET receipt. Старый сохранённый объект задания рассматривается как черновик и не даёт права автоматически отправить подтверждение. Отсутствие результата требует нового просмотра и явного подтверждения.

Редактор строки отправляет только поля, изменённые пользователем, и сохраняет ранее явные исправления. Например, правка примечаний не выбирает первый из двух исходных телефонов. Повторные соответствия «Серия паспорта» или «Номер паспорта» отклоняются до расчёта/применения; пользователь должен оставить по одной колонке каждого вида. Повторные обычные поля сохраняют все варианты и дают конфликт. Инициалы в любых колонках требуют отдельного выбора идентичности даже после подтверждения предупреждений. Строки с ошибками формул сохраняются в предпросмотре; повторный заголовок распознаётся только по непустому распознанному тексту без ошибок ячеек.

Перед записью заново строится индекс кандидатов по транзакционному снимку, включая исправленные значения, архивные и ручные карточки. Изменение кандидатов/карточек отменяет транзакцию, сбрасывает старые решения и создаёт новую версию плана; нужен повторный просмотр. Конкурирующие изменения обнаруживаются снимком значений и `updatedAt`, а блокировки записи SQLite предотвращают запись на устаревший снимок.

## Пределы и поддержка форматов

Пределы определены в `limits.ts`: 12 файлов, 10 МБ на файл, 30 МБ на пакет, 40 МБ распакованного содержимого на файл, 12 МБ на XML-часть, 1500 ZIP-частей, 60 таблиц, 10 000 строк, 100 колонок, 10 000 символов на ячейку. До создания объектов проверяются пути, размеры ZIP, DTD/сущности, глубина XML, разреженные XLSX-диапазоны и число DOCX-строк/тегов. Части распаковываются через потоки с проверкой фактического размера. XML и формулы не загружают внешние ресурсы.

До двух разборов одновременно, восемь заданий, до 24 МБ сериализованных данных одного задания и 64 МБ для всех заданий; TTL 30 минут. Проверка временного бюджета 20 секунд стоит в циклах и между стадиями. Синхронные операции библиотек не прерываются посреди вызова; фактическая память библиотек также превышает сериализованный размер задания. Для строгого ограничения CPU/RSS нужен отдельный процесс разбора. Текущие пределы могут отклонить пакет раньше ограничения по числу строк, если в нём много источников и конфликтов; сообщение предлагает разделить пакет.

Поддерживаются DOCX-таблицы тела документа и XLSX-листы, многострочные заголовки, простые маски числовых номеров с ведущими нулями/`+`, строковые/ISO/Excel-даты (1900 и 1904), rich text и сохранённые результаты формул. Даты текстом: `YYYY-MM-DD`, `DD.MM.YYYY`. Несохранённые формулы, неоднозначные/невозможные даты и числовая точность требуют исправления или исключения. Номера со сложной Excel-маской требуют проверки. OCR, старые DOC/XLS, пароль, вложенные DOCX-таблицы и таблицы колонтитулов не импортируются; вложенная таблица помечает ячейку предупреждением. Исходные объединённые значения не распространяются на других людей.

Поиск кандидатов консервативен: паспорт без пробелов, ФИО с нормализацией пробелов/регистра/ё, телефон с удалением форматирующих символов, инициалы и одна вставка/удаление/замена буквы в фамилии до 80 символов, включая первые буквы. Индекс строится по сигнатурам удалений, затем проверяется расстояние и имя. Точное совпадение доступно для любой длины; для других вариантов написания есть ручной поиск. База ограничена 100 000 карточек на индекс. Полное совпадение полей после нормализации сохраняет исходное написание базы.

## Проверки

`./node_modules/.bin/tsx --test tests/batch-import*.ts`

Тесты используют синтетические офисные архивы в памяти; DATABASE_URL и DATA_DIR задаются абсолютными временными путями до импорта модулей базы/авторизации. Проверяются парсеры, конфликты, ручное объединение, архив, FTS, реальные API handlers в контексте Next request storage, авторизация, откат второй записи, устаревший снимок, новые кандидаты и устойчивый повтор. Браузерная и платформенная приёмка остаются отдельной проверкой.

Regression-набор воспроизводил два P1 обработчиками самих React-компонентов с контролируемым hook state, fetch и sessionStorage: первый POST при «чтении результата» после неудачного GET и неявный выбор телефона при правке заметки. До исправлений оба теста падали. Пять серверных замечаний также воспроизведены падающими тестами. Для XLSX тест перехватывает load книги и доказывает отказ до выделения её структур. После исправления focused-набор содержит 45 успешных тестов; проверка типов проходит. Hook-harness проверяет обработчики, не подменяет браузерную приёмку.

Контрольный замер 11.10.2026 на текущем macOS workspace: 2000 людей, 4000 строк двух файлов XLSX/DOCX, 65 968 байт загрузки; разбор 352 мс, план 254 мс, сериализованное задание 8 016 227 байт. Это искусственный набор с пустым индексом базы; измерение не доказывает такую же скорость на реальной базе, Windows или сложных документах.
